# CQA — Conversation Quality Analytics

Прототип для хакатона Freedom Broker: автоматическая оценка работы оператора в чатах и звонках по настраиваемому чек-листу, объяснения со ссылками на реплики, апелляции и пересмотр.

## Быстрый запуск

Нужны Docker и Docker Compose.

```bash
cp .env.example .env        # впишите GEMINI_API_KEY и DATASET_API_URL
docker compose up -d --build
open http://localhost:8090  # порт задаётся APP_PORT
```

Без `GEMINI_API_KEY` приложение работает в **mock-режиме** (простые эвристики вместо LLM, в UI видна пометка), этого хватает для проверки интерфейса.

Демо-диалоги без доступа к API: «Диалоги → Загрузить JSON → `samples/demo_dialogs.json`».

## Настройки (`.env`)

| Переменная | Назначение |
|---|---|
| `DATASET_API_URL` | GET API организаторов. Либо URL с `{group_id}`, либо базовый URL, к которому добавляется `?group_id=…` |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | Модель оценки, по умолчанию `gemini-2.5-flash` |
| `GEMINI_THINKING_BUDGET` | `-1` — по умолчанию модели, `0` — без рассуждений (дешевле) |
| `PRICE_INPUT_PER_M`, `PRICE_OUTPUT_PER_M` | Цена за 1M токенов для расчёта стоимости одной оценки |
| `BATCH_CONCURRENCY` | Сколько диалогов оценивается параллельно |
| `APP_PORT`, `DB_PORT` | Порты на 127.0.0.1 (приложение / PostgreSQL) |

## Вход (продовый стенд)

На https://assistant.miraitech.health приложение закрыто Google-входом для аккаунтов `@miraitech.health`. Используется общий для сервисов MiraiTech шлюз: nginx `auth_request` + `oauth2-proxy`, сниппеты `/etc/nginx/snippets/oauth2-gate.conf` и `oauth2-api.conf`.

- Без входа страницы перенаправляют на Google, а `/api/*` отвечает 401. Фронтенд в этом случае сам отправляет пользователя на вход.
- nginx передаёт почту вошедшего в заголовке `X-Auth-Email`. Бэкенд записывает её как автора апелляции и как проверяющего.
- При локальном запуске (`localhost:8090`) шлюза нет, и поля автора и проверяющего заполняются вручную.

## Сценарий демо

1. **Диалоги → Импорт из API**, `group_id = DEV` (или контрольный). Затем **Оценить новые**: пакет идёт в фоне, прогресс и стоимость видны вверху таблицы.
2. **Карточка диалога**: итог (кольцо), результаты секций, флаг грубой ошибки. По каждому критерию: ответ, баллы с учётом веса и перераспределения N/A, объяснение и реплики-доказательства. Клик по реплике прокручивает транскрипт; у звонков запись проигрывается с этого места. Для пропущенного действия подсвечивается проверенный участок, для N/A показана причина.
3. **Оспорить оценку** в критерии: комментарий сохраняется как апелляция.
4. **Апелляции**: проверяющий видит спорную оценку, комментарий и фрагмент диалога, подтверждает или меняет оценку с причиной. Итог пересчитывается; в карточке видны исходная оценка, решение и финальный результат.
5. **Чек-листы**: можно поменять критерий (формулировку, тип, вес, N/A, шкалу), затем **Сохранить новую версию** и **Применить к набору**. Старые оценки остаются привязаны к своей версии.
6. **Аналитика**: средний итог, разбивка по языкам, распределение баллов, ответы по критериям, стоимость одной оценки, экспорт CSV.

## Архитектура

```
frontend/              чистые HTML/CSS/JS (ES-модули), без сборки
  index.html           оболочка; window.CQA_CONFIG.apiBase задаёт адрес API
  js/api.js            клиент REST API
  js/views/*.js        экраны: render(root, params) монтируется в любой контейнер
backend/app/
  main.py              FastAPI: REST API + раздача фронтенда
  scoring.py           детерминированный расчёт баллов (веса, шкалы, N/A, округление)
  llm.py, prompt.py    промпт и вызов Gemini (structured JSON output)
  evaluator.py         оценка диалога и пакеты, нормализация ответов модели
  dataset.py           импорт из API организаторов и из JSON
  schema.sql           схема PostgreSQL
  default_checklist.json  начальный чек-лист из PDF
```

**Кто что считает.** LLM возвращает только ответ по каждому критерию (да / нет / N/A / ступень шкалы), объяснение и номера реплик. Баллы, перераспределение веса при N/A, секции, итог и флаг грубой ошибки считает `scoring.py` строго по правилам чек-листа:

- «Да» даёт полный вес, «Нет» — 0;
- шкала пропорциональна весу, верхняя ступень даёт полный вес;
- N/A исключается, и веса нормируются к 100;
- итог округляется до 2 знаков;
- грубые ошибки не влияют на балл и отмечаются отдельно.

Ответы модели проверяются: N/A там, где он не разрешён, заменяется; значение шкалы приводится к ближайшей ступени; номера реплик проверяются на диапазон.

**Хранение.** PostgreSQL:

- `conversations` — диалоги;
- `checklists` — неизменяемые версии чек-листа;
- `evaluations` — исходный и финальный результат;
- `appeals` — апелляции и решения по ним;
- `batches` — пакетные оценки.

**Dynamics 365.** UI не зависит от фреймворков и сборки. Каждый экран монтируется в переданный DOM-узел, адрес API задаётся через `window.CQA_CONFIG.apiBase`. Поэтому файлы можно загрузить как HTML/JS веб-ресурсы, а бэкенд оставить внешним сервисом.

**Стоимость.** Для каждой оценки сохраняются токены (вход и выход, включая thinking) и цена по `PRICE_*`. Средняя стоимость одной оценки видна в «Аналитике» и в карточке. Одна оценка — один вызов модели, при ошибках 429/5xx делаются повторы.

## API (кратко)

`POST /api/datasets/import {group_id}` · `POST /api/datasets/upload` · `GET /api/conversations` · `GET /api/conversations/{id}` · `GET|POST /api/checklists` · `POST /api/evaluations {conversation_id, checklist_id}` · `POST /api/batches {group, checklist_id, only_missing}` · `POST /api/appeals` · `POST /api/appeals/{id}/decision {decision: confirm|change, new_answer, reason}` · `GET /api/stats` · `GET /api/export.csv`
