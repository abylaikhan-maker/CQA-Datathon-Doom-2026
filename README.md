# CQA — Conversation Quality Analytics

Прототип для хакатона Freedom Broker: автоматическая оценка работы оператора в чатах и звонках по настраиваемому чек-листу, объяснения со ссылками на реплики, апелляции и пересмотр.

## Быстрый запуск

Нужны Docker и Docker Compose.

```bash
cp .env.example .env        # впишите GEMINI_API_KEY и DATASET_API_URL
docker compose up -d --build
open http://localhost:8090  # порт задаётся APP_PORT
```

Без `GEMINI_API_KEY` приложение работает в **mock-режиме** (простые эвристики вместо LLM, в UI видна пометка), этого хватает для проверки интерфейса.

Демо-диалоги без доступа к API: «Диалоги → Загрузить JSON → `samples/demo_dialogs.json`».

## Настройки (`.env`)

| Переменная | Назначение |
|---|---|
| `DATASET_API_URL` | GET API организаторов. Либо URL с `{group_id}`, либо базовый URL, к которому добавляется `?group_id=…` |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | Модель оценки, по умолчанию `gemini-2.5-flash` |
| `GEMINI_THINKING_BUDGET` | `-1` — по умолчанию модели, `0` — без рассуждений (дешевле) |
| `PRICE_INPUT_PER_M`, `PRICE_OUTPUT_PER_M` | Цена за 1M токенов для расчёта стоимости одной оценки |
| `BATCH_CONCURRENCY` | Сколько диалогов оценивается параллельно |
| `APP_PORT`, `DB_PORT` | Порты на 127.0.0.1 (приложение / PostgreSQL) |

## Стенд

Стенд открыт по IP без входа: http://34.158.228.29 (nginx → 127.0.0.1:8090, конфиг `deploy/nginx-cqa-ip.conf`).

- Входа нет, поэтому поля автора апелляции и проверяющего заполняются вручную.
- nginx сбрасывает заголовок `X-Auth-Email`: подставить чужую почту снаружи нельзя. Если перед приложением снова поставить шлюз входа, бэкенд возьмёт почту из этого заголовка.
- Модель задаётся в `.env` (`GEMINI_MODEL`); на стенде сейчас `gemini-3.8-flash`.

## Сценарий демо

1. **Диалоги → Импорт из API**, `group_id = DEV` (или контрольный). Затем **Оценить новые**: пакет идёт в фоне, прогресс и стоимость видны вверху таблицы.
2. **Карточка диалога**: итог (кольцо), результаты секций, флаг грубой ошибки. По каждому критерию: ответ, баллы с учётом веса и перераспределения N/A, объяснение и реплики-доказательства. Клик по реплике прокручивает транскрипт; у звонков запись проигрывается с этого места. Для пропущенного действия подсвечивается проверенный участок, для N/A показана причина.
3. **Оспорить оценку** в критерии: комментарий сохраняется как апелляция.
4. **Апелляции**: проверяющий видит спорную оценку, комментарий и фрагмент диалога, подтверждает или меняет оценку с причиной. Итог пересчитывается; в карточке видны исходная оценка, решение и финальный результат.
5. **Чек-листы**: можно поменять критерий (формулировку, тип, вес, N/A, шкалу), затем **Сохранить новую версию** и **Применить к набору**. Старые оценки остаются привязаны к своей версии.
6. **Аналитика**: средний итог, разбивка по языкам, распределение баллов, ответы по критериям, стоимость одной оценки, экспорт CSV.
7. **Регламенты**: загрузите регламент компании (PDF, DOCX, TXT или Markdown; для демо — `samples/demo_regulation.md`). Файл делится на пункты («2.1», «п. 3.4», иначе по абзацам). В карточке разговора **Сверить с регламентом**: модель находит обещания оператора (сроки, суммы, условия, запреты) и ставит рядом пункт регламента с вердиктом «Соответствует», «Расходится» или «Нет в регламенте». Цитаты оператора сверяются с расшифровкой, ключи пунктов — с загруженными файлами. На баллы чек-листа сверка не влияет. **Сверить набор** проверяет все разговоры в фоне.

## Архитектура

```
frontend/              чистые HTML/CSS/JS (ES-модули), без сборки
  index.html           оболочка; window.CQA_CONFIG.apiBase задаёт адрес API
  js/api.js            клиент REST API
  js/views/*.js        экраны: render(root, params) монтируется в любой контейнер
backend/app/
  main.py              FastAPI: REST API + раздача фронтенда
  scoring.py           детерминированный расчёт баллов (веса, шкалы, N/A, округление)
  llm.py, prompt.py    промпт и вызов Gemini (structured JSON output)
  evaluator.py         оценка диалога и пакеты, нормализация ответов модели
  dataset.py           импорт из API организаторов и из JSON
  schema.sql           схема PostgreSQL
  default_checklist.json  начальный чек-лист из PDF
```

**Кто что считает.** LLM возвращает только ответ по каждому критерию (да / нет / N/A / ступень шкалы), объяснение и номера реплик. Баллы, перераспределение веса при N/A, секции, итог и флаг грубой ошибки считает `scoring.py` строго по правилам чек-листа:

- «Да» даёт полный вес, «Нет» — 0;
- шкала пропорциональна весу, верхняя ступень даёт полный вес;
- N/A исключается, и веса нормируются к 100;
- итог округляется до 2 знаков;
- грубые ошибки не влияют на балл и отмечаются отдельно.

Ответы модели проверяются: N/A там, где он не разрешён, заменяется; значение шкалы приводится к ближайшей ступени; номера реплик проверяются на диапазон.

**Хранение.** PostgreSQL:

- `conversations` — диалоги;
- `checklists` — неизменяемые версии чек-листа;
- `evaluations` — исходный и финальный результат;
- `appeals` — апелляции и решения по ним;
- `batches` — пакетные оценки.

**Dynamics 365.** UI не зависит от фреймворков и сборки. Каждый экран монтируется в переданный DOM-узел, адрес API задаётся через `window.CQA_CONFIG.apiBase`. Поэтому файлы можно загрузить как HTML/JS веб-ресурсы, а бэкенд оставить внешним сервисом.

**Стоимость.** Для каждой оценки сохраняются токены (вход и выход, включая thinking) и цена по `PRICE_*`. Средняя стоимость одной оценки видна в «Аналитике» и в карточке. Одна оценка — один вызов модели, при ошибках 429/5xx делаются повторы. На наборе DEV (65 диалогов) с `gemini-2.5-flash` одна оценка стоит в среднем **≈ $0.01** и занимает ≈ 16 с. С `GEMINI_THINKING_BUDGET=0` она стоит ≈ $0.005 и занимает ≈ 6 с, но точность ниже, поэтому по умолчанию рассуждения включены.

**Уточнения к критериям.** Кроме формулировки из PDF, у каждого критерия есть поле «Уточнения для оценки» (`guidance`). В нём описаны пограничные случаи: что считать N/A, чем 4 отличается от 7 по шкале 06, что не считается нарушением. Поле редактируется в «Чек-листах» и попадает в промпт. Памятка со стр. 3 PDF перенесена в «Общие правила».

**Звонки.** Перед оценкой точные дубли реплик (тот же говорящий, время и текст) пропускаются. Реплики, сказанные пока клиент был на удержании, помечаются для модели как внутренние: клиент их не слышал. Нумерация реплик при этом не меняется. Ссылка организаторов на запись — это HTML-страница с mp3 по подписи, которая действует около часа. Поэтому `GET /api/audio/{id}` один раз скачивает файл в кэш и отдаёт его с поддержкой перемотки. Карточка сопоставляет время транскрипта с позицией в записи: учитывает начало записи, вырезанную паузу (по фактической длительности файла) и запускает воспроизведение на 3 с раньше метки.

## Замер точности и версии системы

Вкладка **«Точность»** сравнивает исходные ответы модели (до апелляций) с ручной разметкой. Эталон используется только для замера и в промпт не попадает.

- **Эталон** загружается JSON-файлом на набор диалогов (`{"labels": {id: {"c01": "yes", "c04": "20", …}}}`). Каждая загрузка — новая неизменяемая версия; точность можно смотреть по любой. Необязательные поля: `_uncertain` (спорные критерии, считаются отдельно), `_kind` (тип диалога для разбивки), `_note`.
- **Версия системы — это прогон** («Новый прогон» на вкладке или «Оценить» в списке диалогов). К прогону автоматически записываются версия чек-листа, модель, бюджет рассуждений, отпечатки системного промпта и кода бэкенда, плюс заметка «что изменили».
- **История версий** показывает по каждому прогону совпадение ответов, долю без спорных меток, разбивку по типам, ошибку итога и стоимость. Любой прогон можно выбрать базой (◎) и увидеть, какие ответы исправились, а какие сломались.
- Детали прогона: точность по критериям и группам (язык, канал, тип), список расхождений со ссылкой на критерий в карточке.

Цикл улучшения: изменить чек-лист, промпт или модель → «Новый прогон» с заметкой → сравнить с предыдущей версией. Повторный прогон той же версии показывает шум: на SYNTH два одинаковых прогона разошлись в 4 ответах из 240.

То же из командной строки (`tools/accuracy.py` использует тот же модуль `backend/app/accuracy.py`):

```bash
python3 tools/accuracy.py --api http://localhost:8090 --batch 4 --compare 3 --show c06     # прогон против прогона
python3 tools/accuracy.py --api http://localhost:8090 --group SYNTH --gt samples/synthetic_ground_truth.json
python3 tools/push_checklist.py --api http://localhost:8090 --note "что изменено"   # загрузить чек-лист из файла новой версией
```

## Выгрузка для хакатона

Установите зависимости из `backend/requirements.txt` и запустите команды из корня репозитория. Подставьте зарегистрированное название команды.

Чтобы выгрузить завершённый пакет из приложения, задайте `DATABASE_URL` для PostgreSQL приложения и передайте ID пакета. Скрипт прочитает исходные оценки модели из этого прогона. Для такого экспорта ключ Gemini не нужен.

```bash
python tools/submit_results.py dev --team "Название команды" --batch 5
```

Чтобы оценить новый набор, задайте `GEMINI_API_KEY` и `GEMINI_MODEL`. Для загрузки из API также задайте `DATASET_API_URL` и подставьте контрольный ID организаторов.

```bash
python tools/submit_results.py dev --team "Название команды" --input /path/to/invoke.json
python tools/submit_results.py prod --team "Название команды" --group "Контрольный ID"
```

Для новой оценки скрипт использует `backend/app/default_checklist.json`, а для `--batch` берёт версию чек-листа сохранённого прогона. Результат записывается в `results/dev/results.json` (60 чатов и 5 звонков), `results/prod/results.json` (10 чатов) или `results/swap/results.json` (3 чата набора Swap). Формат включает исходные ID, восемь критериев, объяснения и номера подтверждающих реплик от 1 по исходной расшифровке. Для новых цитат в `evidence_turns` включаются только ссылки, прошедшие сверку с текстом реплики. Если оценка диалога не удалась, его ID сохраняется с `status: "error"`. Проверьте итоговый список и ошибки перед commit и push.

`POST /api/datasets/import {group_id}` · `POST /api/datasets/upload` · `GET /api/conversations` · `GET /api/conversations/{id}` · `GET /api/audio/{id}` · `POST|GET /api/ground-truth` · `GET /api/accuracy?group=` · `GET /api/accuracy/{batch}?compare=` · `GET|POST /api/checklists` · `POST /api/evaluations {conversation_id, checklist_id}` · `POST /api/batches {group, checklist_id, only_missing}` · `POST /api/appeals` · `POST /api/appeals/{id}/decision {decision: confirm|change, new_answer, reason}` · `GET /api/stats` · `GET /api/export.csv` · `GET|POST /api/regulations?filename=` (тело — файл) · `DELETE /api/regulations/{id}` · `GET|POST /api/regulations/checks/{conversation_id}` · `POST /api/regulations/runs {group}` · `GET /api/regulations/runs/{id}`
